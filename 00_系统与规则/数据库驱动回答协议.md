# 数据库驱动的题目回答与错因诊断协议

## 目的

Hermes 在回答错题、不会做的题或解法核对问题时，先读取与当前题目相关的正式历史记录，再结合用户本次作答进行针对性讲解。数据库用于提供个人证据，不替代对当前题目的独立分析。

本协议不用于主动安排学习。除非用户明确提出复习、复测或错题整理需求，否则不查询或输出到期任务、学习计划和复习日程。

## 触发范围

以下请求适用本协议：

- 用户提交不会做、做错或没有把握的题；
- 用户要求检查答案、解题过程或某一步推理；
- 用户追问自己具体卡在哪个知识点；
- 用户要求结合历史错题进行讲解；
- 用户明确要求复测、整理错题或辅助复习。

纯粹的系统维护问题不执行学习记录查询。

## 核心流程

```text
还原当前题目和用户疑问
→ 提取当前作答中的客观证据
→ 识别科目和候选知识点
→ 只读检索相关 CONFIRMED 历史题目、作答和错误
→ 比较当前解法与正确解法，定位最早偏差
→ 区分表面错误、直接原因和候选根因
→ 根据历史证据调整讲解起点和深度
→ 先解决当前问题
→ 必要时生成待审核诊断候选
→ 回答前自审
```

## 第一步：还原当前问题

回答前先确认：

- 题目条件、问题目标和图表信息是否完整；
- 用户希望得到提示、完整解答、步骤检查还是错因分析；
- 用户已经做到哪一步，具体从哪里开始不确定；
- 用户是否独立作答、使用过提示或看过答案。

缺失信息不影响解题时直接回答。只有缺失信息会改变结论或诊断时才提问，每次最多3个，不为完善档案打断当前解题。

## 第二步：只读查询个人历史

使用 `09_数据库/queries/learning_context.sql`，通过 `09_数据库/db_access.py` 的只读入口查询。查询顺序为：

1. 候选知识点的 CONFIRMED 掌握证据；
2. 相同知识点上的历史题目和作答；
3. 用户的答案路径、正确性、耗时、提示次数、是否独立和是否看答案；
4. 相同知识点上的已确认错误和未解决错误；
5. 相邻知识点或已确认前置关系；
6. 相关 PENDING proposal，仅作为待确认提醒；
7. 用户明确要求复习相关帮助时，才查询历史复测和复习记录。

查不到记录时必须明确写明“暂无相关个人历史证据”，不得把空数据解释为未接触、薄弱或已经掌握。

## 第三步：错因诊断

诊断从当前作答中最早出现的实质偏差开始，不只依据最终答案对错。依次检查：

1. **题意与条件**：是否漏看条件、误读范围、混淆求解目标；
2. **知识点**：是否不知道定义、定理、公式或适用条件；
3. **方法选择**：是否知道知识但没有识别应使用的方法；
4. **推理过程**：是否存在跳步、方向错误或论证缺口；
5. **计算与表达**：是否为符号、算术、书写或语言表达问题；
6. **答案核对**：题目、参考答案或标准解本身是否可能有误。

`surface_error` 可以描述观察到的错误表现；`direct_cause` 和 `root_cause` 属于推断，在用户批准前必须保持 PROPOSED。一次作答不足以证明稳定的深层根因。

只有出现以下证据时，才可以在候选诊断中指出“可能为重复问题”：

- 历史中存在相同或相邻知识点的 CONFIRMED 错误；
- 当前作答出现可比对的相同错误位置或模式；
- 两次记录的题目条件和解题任务具有可比性。

## 第四步：个性化讲解

讲解必须先解决用户当前问题，再体现个性化：

- 无个人历史证据：从题目所需的最小前置内容讲起，不推测用户水平；
- 有相同错误历史：明确指出关联依据，并重点解释重复卡点；
- 概念不清：讲定义、适用边界和最小例子；
- 方法未识别：讲识别信号和为什么选择该方法；
- 推理中断：从断点续讲，不重复用户已经正确完成的部分；
- 仅为计算失误：简洁纠正并给出检查方法，不扩大为知识点不会；
- 已有高等级 CONFIRMED 证据：减少基础重复，直接处理变式或边界；
- 历史证据冲突：说明冲突，不擅自选择对用户更不利或更有利的结论。

同类题、变式题和复测题可以作为可选支持，但不得取代当前题目的讲解，也不得自动生成学习日程。

## 第五步：回答后的记录候选

可以提取的客观信息包括：日期、科目、题目来源、题目原文路径、用户答案路径、作答结果、用时、提示次数、是否看答案和是否独立完成。

以下内容只能生成 proposal：

- 题目与知识点的归属关系；
- 错误的直接原因和根因；
- 掌握度变化或“已经学会”的判断；
- 是否需要补充前置知识；
- 复习或复测建议及日期；
- 长期学习计划调整。

复习日期只在用户明确要求安排时生成。proposal 未获批准前不得影响后续正式诊断或复习调度。

## 回答呈现原则

根据问题复杂度自然组织回答，不强制每次显示固定表格。通常优先包含：

1. 当前题目的直接结论或关键卡点；
2. 针对用户作答的讲解；
3. 与历史记录的关联，仅在确有证据时出现；
4. 候选诊断和不确定性；
5. 用户明确要求时提供同类题、复测或复习支持。

不得因为系统需要记录数据而让回答变成冗长的管理报告。

## 回答前自审摘要

每次回答学习问题前输出简洁自审摘要，至少检查：

- 题目条件和用户疑问是否理解完整；
- 公式、定理、语法或方法的适用条件是否满足；
- 关键推理、计算或来源是否核对；
- 引用的个人历史是否为 CONFIRMED；
- 当前结论、历史事实和候选诊断是否清楚区分；
- 是否存在需要教材、标准答案或用户补充才能解决的不确定项。

## ChatGPT 网页版适配

ChatGPT 网页版不能直接读取本地 SQLite 数据库。由 Hermes 按当前题目的科目和候选知识点生成最小必要上下文，供用户上传或复制给 ChatGPT。上下文应优先包含相关历史题目、作答和已确认错误，不默认包含到期复习任务，也不得声称已经自动共享数据库。
