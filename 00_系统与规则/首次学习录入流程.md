# 首次题目与作答录入流程

## 整体流程

```
用户提供不会做、做错或需要核对的题目
→ Hermes 识别科目和候选知识点
→ 查询相关个人历史
→ 数据为空则明确说明“暂无相关个人历史证据”
→ ChatGPT 或 Hermes 进行教学
→ 用户真实作答
→ 记录客观数据
→ 按需生成知识点归属、错误原因和掌握度候选（proposal）
→ 用户审批
→ 正式写入
```

## 第一步：用户提供内容

用户将题目、作答过程、参考答案或资料放入 `01_收件箱/待处理/`，或在聊天中直接提出。

## 第二步：空数据处理

数据库查询后，如果对应科目或知识点没有任何记录，**必须明确输出“暂无相关个人历史证据”**，不得：

- ❌ 默认用户掌握度
- ❌ 推测用户基础水平
- ❌ 自动判断用户薄弱
- ❌ 创建复习日期
- ❌ 创建错误记录
- ❌ 声称用户已经学过某个知识点

应当先解决当前题目，并在需要诊断时优先确认：
1. 用户具体卡在哪一步；
2. 是否独立完成；
3. 是否使用提示或查看答案。

每次最多提出 3 个高价值问题。

## 第二点五步：知识点登记（首次正式沉淀时处理）

`knowledge_points` 表初始为空。用户提供题目或主题后，Hermes 识别出候选知识点，**知识点本身的创建也要走 proposal 流程**：

```
识别题目涉及的知识点（候选名称+所属科目+前置关系）
→ 生成知识点创建 proposal（PROPOSED）
→ 用户审批
→ 知识点写入 knowledge_points（CONFIRMED）
→ 题目/作答记录才能关联到该知识点
```

知识点 proposal 必须包含：
- 知识点名称（如"极限的等价无穷小替换"）
- 所属科目（subject_id）
- 前置知识点（如有，parent_id 或 prerequisite 关系）
- 依据（为什么属于这个科目/层级）
- 置信度

知识点创建与后续学习记录的关系：
1. 知识点未创建时，题目只能先记录客观作答（日期、答案、用时等）
2. 掌握度、错误、复习等判断必须等知识点 CONFIRMED 后才能关联
3. 一个题目可能涉及多个知识点，逐一确认后建立 question_knowledge_points 关联

## 第三步：针对当前题目讲解

由 ChatGPT 或 Hermes 根据用户当前疑问进行讲解。无历史数据时，从解决当前题目所需的最小前置内容开始，不把用户默认标记为“未接触”或任何掌握等级；有 CONFIRMED 历史证据时，按 `数据库驱动回答协议.md` 调整讲解起点和深度。

## 第四步：客观数据记录

### 可以直接记录的客观数据

以下信息在用户完成当前题目处理后可以直接记录到数据库（无需审批）：

| 字段 | 说明 |
|------|------|
| 日期 | 学习发生的实际日期 |
| 科目 | 数学一 / 英语一 / 思政 / 专业课 |
| 题目主题 | 用户提交的题目或疑问 |
| 题目来源 | 教材名称、真题年份、网课等（**应先登记到 resources 表并关联 source_resource_id**） |
| 用户答案 | 用户实际给出的答案（存入 Markdown 文件，attempts.my_answer_path 指向该文件） |
| 是否正确 | 对/错/部分正确 |
| 用时 | 完成题目所用的时间（秒） |
| 提示次数 | 用户要求提示的次数 |
| 是否看答案 | 是否在作答前查看了标准答案 |
| 是否独立完成 | 是否在没有外部帮助的情况下完成 |

### 题目处理会话记录要求（正式沉淀时）

每次正式沉淀题目与作答时创建一条 study_sessions 记录，且 **summary_path 不能为空**——必须指向当日题目处理记录 Markdown 文件：

- 文件位置：`03_学习记录/每日/YYYY-MM-DD_科目_题目主题.md`
- 文件内容：题目、用户作答、关键卡点、讲解和处理结果
- 数据库 study_sessions.summary_path 填写该文件的相对路径

### 必须生成 proposal 的数据

以下信息只能生成 proposal，走审批流程后方可写入正式表：

| 数据 | 说明 |
|------|------|
| 错误根因 | 表面错误、直接原因、深层原因的分析 |
| 掌握度变化 | 掌握等级（0-5）的认定 |
| 是否已经学会 | 是否达到了不再需要定期复习的程度 |
| 下次复习日期 | 根据掌握度建议的下次复习时间 |
| 是否回退前置知识 | 是否需要补习更基础的知识点 |
| 长期学习计划调整 | 对整个学习计划的调整建议 |

### 按需复习日期计算规则（用户明确要求时）

系统不主动生成复习日期。用户明确要求安排复习或复测时，候选日期**必须按规则计算**，不得手写随意日期：

- 完全不会 → 当天（+0 天）
- 需要明显提示 → +1 天
- 独立但较慢 → +3 天
- 正确且熟练 → +7 天
- 延迟复测正确 → +14 天
- 多次稳定正确 → +30 天
- 综合迁移成功 → +45~60 天

计算公式：`next_review_date = 今天 + N 天`（以日期格式 YYYY-MM-DD 写入 reviews.scheduled_date）。

### change_log 粒度要求（模拟验证发现）

每次正式写入必须对应一条 change_log 记录：

- 一条 proposal 对应一条 change_log（proposal_id 关联）
- 如果一次审批批处理了多条 proposal，每条 proposal 各写一条 change_log
- 不得用一条 change_log 概括多个不同 proposal 的修改

## 第五步：审批

当前问题解决后，如产生需要正式沉淀的候选判断，再集中输出待审核项。审批选项：

- **全部批准**：所有候选一次性通过
- **修改后批准**：指定修改其中某些候选后通过
- **拒绝**：驳回候选
- **暂缓**：推迟决定

## 第六步：正式写入

用户批准后，通过 `db_access.py` 的受控入口执行写入：
1. 开启事务
2. 执行修改
3. 检查影响行数
4. PRAGMA foreign_key_check
5. PRAGMA quick_check
6. 提交或回滚
7. 写入 change_log

## 注意事项

- 不得为了测试系统而虚构任何学习数据
- 不得创建虚假的学习会话、题目、作答、错误、掌握度、复习记录
- 首次真实题目记录应当标注为首次记录；除非有明确证据，不得因此认定为该知识点的“首次接触”
