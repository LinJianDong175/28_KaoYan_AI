# 审批规则

## 审批流程

所有正式学习判断必须经过以下完整流程：

```
proposal
→ 用户审核
→ approvals
→ 正式表修改
→ change_log
```

## proposal 必须包含的字段

| 字段 | 说明 |
|------|------|
| proposal_id | 唯一标识 |
| proposal_type | 建议类型 |
| target_table | 目标表名 |
| target_record | 目标记录标识 |
| old_value | 修改前值 |
| proposed_value | 建议修改值 |
| reason | 修改理由 |
| evidence | 证据描述 |
| source_ids | 证据来源ID |
| confidence | 置信度（0-1） |
| impact | 对学习和复习的影响 |
| rollback_plan | 反向撤销方法 |
| status | 状态（PENDING） |
| created_at | 创建时间 |

## 用户审批选项

- 批准
- 修改后批准（需提供修改值）
- 拒绝
- 暂缓
- 要求重新分析

## 审批后执行

1. 用户审批决定写入 `approvals` 表
2. 正式执行修改（事务内）
3. 修改前后值写入 `change_log` 表
4. 更新相关 Markdown 记录

## 历史记录处理

Markdown中的"已批准"必须能够对应数据库记录。无法找到明确审批证据的旧版流程记录，应注明"旧版正式审批流程启用前，经用户会话明确授权执行"。不得伪造历史 proposal 或 approval 记录。

## 可自动执行

只读扫描、索引草稿、缺失字段检查、重复检查、统计草稿、数据库完整性验证、生成 proposal、一致性检查。

## 必须审核后执行

掌握度、错误根因、复习日期、知识点关系、知识点是否学会、长期计划、院校/考试科目结论、批量写入、数据库结构、删除/覆盖/移动原始资料、覆盖正式 Markdown 记录。

## 禁止自主执行

删除原始资料、越界操作、系统设置修改、软件安装、操作用户账号、发送邮件、提交报名、保存秘密、自行确定目标院校或考试科目、创建任何备份、创建数据库副本或快照、删除数据库。
